배경Background

제로콜의 전화는 학원의 대표번호로 걸려 옵니다. 배포가 잘못되면 그 번호가 안 받아지고, 되돌리는 동안에도 고객 전화는 계속 걸려 옵니다.ZeroCall carries an academy’s main line. A bad release means that number stops answering — and customers keep calling while you roll back.

고쳐 보고 아니면 되돌리는 방식이 통하지 않는 시스템에서, 무엇을 어떻게 확인해 왔는지에 대한 기록입니다.This is a record of what I verify, and how, in a system where "try it and roll back" is not available.

단위 시험이 닿지 못하는 곳Where unit tests cannot reach

단위 시험이 닿지 못하는 구간이 있습니다. 살아 있는 DB·API·교환기가 있어야만 확인되는 것들입니다. 그런 구간을 위해 시험 층을 따로 만들었습니다.Some things unit tests can never reach — they only show up against a live database, API and exchange. Those got their own test layers.

① 시나리오 시험① Scenario tests

발신번호를 고르는 판단이 서버 코드에 없습니다. 다이얼플랜 설정의 SQL이 유일한 구현이라 단위 시험이 닿지 못합니다. 그래서 시험 스크립트가 그 파일에서 쿼리를 그대로 꺼내 실제 DB에 돌립니다 — 손으로 옮겨 적으면 원본과 갈라져 시험이 거짓말을 합니다.The logic choosing a caller ID is not in the server code. Its only implementation is SQL inside the dialplan, which unit tests never see. So the script lifts the query out of that file and runs it against the real database — transcribe it and the test starts lying.

고객사 사이의 권한 경계가 지켜지는지, 모든 노드가 같은 다이얼플랜을 들고 있는지도 함께 봅니다. 시험은 자기가 바꾼 값을 되돌립니다.It also checks that tenant boundaries hold, and that every node carries the same dialplan. Each test puts back what it changed.

② 부하 시험 — CPU를 보지 않는다② Load testing — CPU is the wrong gauge

통화 한 건마다 UDP 소켓 하나와 20ms 주기 루프 두 개가 열립니다. 초당 100회 타이머와 100패킷이 전부 단일 이벤트 루프 위에서 돕니다. 루프가 밀리면 RTP 간격이 흔들려 CPU가 여유 있는데 음질이 먼저 무너집니다.Each call opens a UDP socket and two 20 ms loops — 100 timers and 100 packets a second, all on one event loop. When it slips, RTP jitters and audio degrades while CPU still looks fine.

그래서 판정 기준은 이벤트 루프 지연 p99 20ms입니다. 그 지점이 인스턴스당 정원이고, 올림(회선 한도 ÷ 정원)이 필요한 대수입니다.So the gauge is event-loop lag p99 at 20 ms. That point is one instance’s capacity, and ceil(line limit / capacity) is how many you need.

25 → 50 → 100 → 200으로 올리며 각 단계를 10분 이상 유지합니다. 한 번에 최대치를 때리면 어디서 무너졌는지 못 봅니다.Ramp 25 → 50 → 100 → 200, ten minutes per step — hit the top at once and you cannot see where it broke.

③ AI 응대는 말을 걸어서 확인한다③ The AI agent is tested by talking to it

응답 문자열을 비교해서는 검증되지 않습니다. 마이크로 직접 말을 걸면서 에이전트가 어떤 도구를 어떤 인자로 호출했는지와 전문 저장 여부를 함께 보는 디버거를 만들었습니다. 통화를 걸지 않고도 응대 흐름을 끝까지 밟습니다.You cannot verify a voice agent by diffing strings. I built a debugger that lets me speak to it while showing which tools it called and with what arguments, and whether the transcript was stored — the whole flow, without placing a call.

시험 문서에 "함정" 목록을 둡니다. 두 API가 같은 토큰 클레임을 반대로 해석해 모든 요청이 401인데 "거부됐으니 통과"로 읽은 일, 순차 분배가 자리마다 15초를 소요한다는 점을 모르고 20초에 보고 판정한 일. 시험이 틀리는 방식은 대개 실패를 성공으로 읽는 쪽입니다.The docs carry a list of traps: two APIs reading the same token claim in opposite directions, so everything 401’d and I read "rejected, therefore passed"; judging at twenty seconds when sequential distribution spends fifteen per seat. Tests usually fail by reading a failure as a pass.

배포 안전장치가 작동하지 않고 있었다The release guard was not actually guarding

통화를 처리하는 프로세스를 교체할 때는 통화가 빠질 때까지 기다리도록 되어 있습니다. 그 대기 로직을 점검하다가 결함 세 가지를 발견했습니다. 셋 다 에러 없이 통과하고 있어, 로그만 보아서는 드러나지 않았습니다.Replacing the process that handles calls is supposed to wait for them to drain. Auditing that logic, I found three faults. All three passed without raising anything, so the logs never showed them.

① 주석은 "중단한다"였고 코드는 그대로 통과했다① The comment said "abort"; the code walked on

대기 시간이 상한을 넘기면 중단하도록 되어 있었습니다. 실제로는 경고만 찍고 통과했습니다. 스크립트의 마지막 명령이 로그 출력이라, 그 단계가 성공으로 끝나 버린 것입니다.It was supposed to abort when the wait exceeded its limit. In practice it logged a warning and continued — the last command in the step was the log line itself, so the step exited successfully.

② 절대 오지 않는 순간을 기다리고 있었다② It waited for a moment that never came

"통화가 하나도 없을 때"를 기다렸습니다. 바쁜 시간대에는 그런 순간이 오지 않아서, 늘 상한을 꽉 채우고 타임아웃 경로로만 갔습니다.It waited for "no calls at all". During busy hours that moment never arrives, so it always burned the full timeout and took the timeout path.

그래서 기준을 "무엇이 실제로 깨지는가"로 좁혔습니다. 상담원과 연결된 통화와 대기 중인 통화는 교체해도 다음 인스턴스가 이어받습니다. ARS와 AI 응대만 미디어가 이 프로세스를 지나므로 그 자리에서 깨집니다. 그 통화만 확인하면 됩니다.So the test became "what actually breaks?" Calls connected to an agent and calls waiting in queue are picked up by the next instance. Only IVR and AI calls route media through this process, so only those break — and only those need checking.

③ 조회 실패를 "통화 없음"으로 읽고 있었다③ A failed query read as "no calls"

가장 나쁜 것이었습니다. 교환기에 통화 수를 묻는데, 응답이 없으면 그 값이 0으로 떨어졌습니다. 그러면 "통화가 없다"가 되어 교체가 진행됩니다.This was the worst one. It asked the PBX how many calls were live, and a failed query came back as zero. Zero means "no calls", so the replacement proceeded.

즉 교환기가 이상할 때 가장 확신을 갖고 교체하고 있었습니다. 안전장치가 정확히 위험한 순간에 반대로 작동한 것입니다. 지금은 살아 있는지 먼저 확인하고, 계속 대답이 없으면 중단합니다.In other words, it replaced most confidently exactly when the PBX was unhealthy. The safety check inverted itself at the one moment it mattered. Now it verifies the PBX is answering at all, and aborts if it stays silent.

고친 뒤에는 교환기 스텁을 만들어 다섯 경로를 전부 돌렸습니다 — 조용해짐 · 계속 바쁨 · 위험한 통화 잔존 · 도중에 사라짐 · 교환기 무응답. 배포 스크립트는 평소에 안 도는 경로가 많아서, 그 경로를 일부러 만들어 보지 않으면 다음에 또 같은 식으로 조용히 틀립니다.Afterwards I stubbed the PBX and exercised all five paths — goes quiet, stays busy, risky calls remain, calls vanish mid-wait, PBX unresponsive. Deploy scripts are mostly branches that never run in normal times; unless you force them, they go on failing silently.

조용한 실패에 대하여On silent failure

여기 모인 결함에는 공통점이 있습니다. 하나도 에러를 내지 않았습니다. 배포는 성공으로 끝났고, 시험은 통과로 읽혔고, 조회는 0을 돌려줬습니다.Every fault here has one thing in common: none of them raised an error. The deploy exited successfully, the test read as a pass, the query returned zero.

그래서 시험 문서에 "함정" 목록을 따로 둡니다. 두 API가 같은 토큰 클레임을 반대로 해석해 모든 요청이 거부됐는데 "거부됐으니 통과"로 읽은 일, 순차 분배가 자리마다 15초를 소요한다는 점을 모르고 20초에 보고 판정한 일 — 전부 실제로 당한 것들입니다.So the test docs carry a list of traps: two APIs reading the same token claim in opposite directions so everything was rejected and I read "rejected, therefore passed"; judging at twenty seconds when sequential distribution spends fifteen per seat. All of them caught me first.

시험이 틀리는 방식은 대개 실패를 성공으로 읽는 쪽입니다. 그래서 "무엇을 확인했는가"보다 "어떤 상태를 만들어서 확인했는가"를 적어 둡니다. 조건이 다르면 같은 이름의 시험이 다른 것을 봅니다.Tests usually fail by reading a failure as a pass. So the docs record what state was constructed rather than what was checked — under different conditions, a test with the same name looks at something else entirely.
