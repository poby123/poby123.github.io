070 전화·문자와 AI 전화 응대를 함께 제공하는 서비스입니다. 통신사 회선을 받는 SIP 프론트엔드부터 교환기, 대기열, ARS, 녹음·전사·요약, 상담원 앱과 PC 에이전트까지 전 구간을 만들었습니다. 지금은 메가스터디 학원 현장에 도입되어 본사와 지점이 함께 쓰고 있습니다. A 070 phone and messaging service with an AI agent that answers calls. I built the whole path: the SIP front end that faces the carrier, the PBX, the queue, the IVR, recording, transcription and summarisation, plus the mobile app and the desktop agent. It is now deployed inside Megastudy’s academies, used by both head office and branches.

  • 교환기부터 직접 세웠습니다. Asterisk를 올리고 다이얼플랜을 작성한 뒤, NestJS로 만든 call-handler를 ARI로 붙여 인입·발신·녹음·전환 흐름을 하나씩 연결했습니다.I stood the exchange up myself. Asterisk, then the dialplan, then a NestJS call-handler attached over ARI — wiring inbound, outbound, recording and transfer one flow at a time.
  • 가입자별 설정은 다이얼플랜에 박지 않고, 통화가 들어올 때 조회하게 만들었습니다. 다이얼플랜은 파일 한 벌로 두고, 착신번호·그룹·착신전환·영업시간은 그때그때 DB에서 읽습니다. 그래서 사용자가 화면에서 바꾼 설정이 교환기를 건드리지 않고 반영되고, 가입하면 SIP 계정도 자동으로 발급됩니다.Per-subscriber settings are looked up when a call arrives, not baked into the dialplan. The dialplan stays a single set of files; the dialled number, group, forwarding and business hours are read from the database at call time. So a change made in the web UI takes effect without touching the exchange, and signing up provisions a SIP account automatically.
  • 단일 Asterisk를 Kamailio + rtpengine 앞단 구조로 전환했습니다. 바깥에서 보이는 주소와 포트를 하나도 바꾸지 않아 통신사 협의도, 현장 전화기 재설정도 없이 끝냈습니다.Replaced a single Asterisk with a Kamailio + rtpengine front end. Not one externally visible address or port changed, so it shipped without renegotiating with the carrier or touching a single phone on site.
  • 대기열과 ARS를 직접 구현했습니다. Asterisk 내장 큐는 단말이 항상 등록돼 있다고 전제하는데, 모바일은 푸시로 깨워야 해서 맞지 않았습니다. 분배기를 Node에서 ARI로 구현했습니다.Wrote the queue and IVR myself. Asterisk's built-in queue assumes endpoints stay registered; mobile endpoints have to be woken by push. So the distributor runs in Node over ARI instead.
  • AI 응대 하네스를 만들었습니다. 업종별 에이전트와 도구를 갈아 끼우고, 실시간 음성 모델을 통화 미디어에 직접 물립니다. 필요하면 대화 도중 사람에게 넘깁니다.Built the AI answering harness — per-industry agents and tools that swap in behind one interface, wired straight into the call's media, and able to hand the caller to a human mid-conversation.
  • 시험 층을 따로 만들었습니다. 단위 시험이 닿지 못하는 다이얼플랜 로직은 원본에서 쿼리를 꺼내 실제 DB에 돌려 확인하고, 처리 용량은 CPU가 아니라 이벤트 루프 지연으로 판정하는 부하 시험으로 잽니다.Built the test layers. Dialplan logic unit tests cannot reach is verified by lifting its query from the source file and running it against the real database; capacity is measured by event-loop lag under load rather than CPU.

통신 표준과 통신사 규격 문서를 근거로 설계했습니다. 서버 모노레포 8개 앱 약 24만 줄에, 관리 웹 3종·모바일 앱·PC 에이전트가 함께 붙어 있습니다. 전화 외에도 문자 송수신(통신사 통합메시징 연동과 전송자격인증 준비), 구독 결제 스케줄링, 고객사 웹사이트에 붙이는 상담 위젯(iframe + postMessage)을 함께 만들었습니다. The design is grounded in the telecom standards and the carrier’s specifications. A server monorepo of 8 apps at ~240k lines, plus three admin web clients, the mobile app and the desktop agent. Beyond calls I also built SMS/MMS (carrier messaging integration and the sender-authentication filings), subscription billing, and the chat widget customers embed in their own sites (iframe + postMessage).

  • 중복 예약을 막는 것이 이 제품의 본질이었습니다. 한 번 겹치면 사장님이 고객에게 사과하고 환불해야 하므로, 플랫폼별 수집 주기를 3분 이내로 유지해야 했습니다. 크롤러를 플랫폼·샤드 단위로 나눠 병렬화하고 Bull 큐로 동기화 순서를 지켰습니다.Preventing double bookings is the product.   • 예약 확정·리마인드·종료 알림톡을 자동 발송합니다. 리마인드에는 예약 종료 시각에 스스로 만료되는 출입 비밀번호 안내 링크를 함께 보냅니다.Automated confirmation, reminder and check-out messages. The reminder carries a door-code page whose link expires by itself when the booking ends.

  • 매출 대시보드와 캘린더를 제공합니다. 일·주·월별 매출과 플랫폼별 비중을 예약 데이터에서 바로 계산합니다. 주 사용자가 40~60대 사장님들이라 화면은 단순하게, 기능은 강하게 잡았습니다.Revenue dashboard and calendar computed straight from reservation data — daily, weekly, monthly, and by platform. 플랫폼 인프라 — k3s 전환Platform infrastructure — moving to k3s

설계 · 구축 · 운영Design, build, operation

서비스가 둘, 셋으로 늘면서 EC2에 흩어진 애플리케이션을 한 곳에서 보기 어려워졌습니다. 서버비와 조직 규모를 고려해 EKS 대신 k3s를 골라 클러스터를 직접 세우고, 애플리케이션 51개를 GitOps로 옮겼습니다. As one service became three, applications scattered across EC2 stopped being legible from one place. Weighing cost against the size of the team, I chose k3s over EKS, stood up the cluster myself, and moved 51 applications onto GitOps.

  • 배포 시점은 사람이 정합니다. CI는 이미지 태그만 커밋하고 Argo CD가 차이를 표시한 채 기다립니다. 이미지 태그는 커밋 SHA로 고정해 "지금 뭐가 떠 있는지"를 git으로 되짚을 수 있게 했습니다.Humans decide when to deploy. CI only commits an image tag; Argo CD shows the drift and waits. Tags are pinned to commit SHAs, so what is running is always traceable back through git.
  • 노드 한 대가 흔들리면 사용자 25%가 실패하던 구조를 개선했습니다. A레코드에 노드 IP를 나열한 라운드로빈 DNS에는 헬스체크가 없습니다. 앞단에 NLB를 세워 L4 패스스루로 흘리도록 바꿨습니다.Fixed a setup where one shaky node failed 25% of users. Round-robin DNS across node IPs has no health check; I put an NLB in front and passed TLS through at L4.
  • 통신사 화이트리스트에 묶인 발신 IP를 전용 노드로 격리했습니다. taint를 걸어 다른 파드가 그 주소로 나가지 못하게 했습니다.Isolated the carrier-whitelisted egress IP onto a dedicated, tainted node so no other pod can leave the cluster through that address.

Terraform과 Argo CD 매니페스트 약 3,900줄 · 커밋 59개. 코드보다 중요한 것이 문서라고 보고, 새 인프라 관리자가 계정 발급부터 클러스터 접근까지 따라올 수 있는 온보딩 문서와 미결 항목을 근거와 함께 남겼습니다.About 3,900 lines of Terraform and Argo CD manifests over 59 commits. Documentation mattered more than the code here: a new maintainer can follow the onboarding from account creation to cluster access, and every open item is written down with its reasoning.

춤춤 (Chumchum)

서버 · 웹 개발 리드Engineering lead — server and web

춤추는 사람들을 위한 댄스 연습실 예약 플랫폼입니다. 게스트 API, 호스트 API, 관리자, 백그라운드 워커로 나눈 모노레포와 호스트·게스트 웹 두 벌을 만들었습니다.A booking platform for dance practice rooms — a monorepo split into guest API, host API, admin and a background worker, plus two separate web clients for hosts and guests.

  • 가장 어려웠던 것은 예약 변경이었습니다. 예약과 결제가 다대다입니다. 한 번의 결제가 여러 예약에 걸쳐 있고, 연속 시간대 묶음 할인 때문에 예약 하나를 취소하면 남은 예약의 가격이 오릅니다. 그래서 환불액은 "환불 가능액 − 남은 예약의 인상분"이고, 그 금액을 감당할 수 있는 결제 건을 골라 거기서 환불합니다.Rebooking was the hard part. Reservations and payments are many-to-many: one payment can cover several bookings, and because consecutive hours are discounted as a block, cancelling one booking raises the price of the ones that remain. So the refund is "refundable amount minus the increase on what is left", charged against a payment large enough to absorb it.
  • 부분 환불과 추가 결제를 한 흐름으로 묶었습니다. 변경 후 금액이 낮아지면 차액을 환불하고, 높아지면 추가로 결제합니다. 취소 수수료도 이 계산에 함께 들어갑니다. 결과가 음수가 되면 지원하지 않는 변경으로 막습니다 — 돈이 맞지 않는 채로 통과시키는 것보다 낫습니다.Partial refunds and top-up charges run through one path. If the new total is lower we refund the difference; if it is higher we charge it, with the cancellation fee folded into the same sum. If the result would be negative the change is rejected as unsupported — better than letting the books go wrong.
  • 예약 리마인드 알림톡, 예약 변경 감시, 정산 모니터링은 별도 워커가 Bull 큐로 처리합니다. 사용자 요청 경로에서 떼어 놓아야 결제 응답이 알림 발송 때문에 느려지지 않습니다.Reminder messages, change monitoring and settlement checks run in a separate worker over Bull queues — off the request path, so a payment response never waits on a notification.
  • 구글·카카오·네이버·애플 소셜 로그인, 호스트의 공간 등록과 가격 설정, 정산까지 직접 만들었습니다.Google, Kakao, Naver and Apple sign-in, host-side space registration and pricing, and settlement — all built in-house.

서버 2만 줄, 호스트·게스트 웹 2만 2천 줄. 두 달 동안 혼자 만들었습니다.20k lines of server and 22k lines across the host and guest web clients — built alone in two months.

프로세스를 셋으로 나눈 이유Why it runs as three processes

처음에는 스레드로 구현했습니다. 센서를 읽는 동안 화면이 얼어붙었습니다. 파이썬 GIL 때문에 스레드로는 센서 대기와 화면 갱신이 실제로 동시에 수행되지 않습니다. 그래서 화면(View) · 백그라운드 핸들러 · 서버 통신(Data Controller) 로 나누고, 하드웨어 제어는 그 아래 별도 모듈로 내렸습니다.I wrote it with threads first, and the screen froze while a sensor was being read — under Python’s GIL, waiting on a sensor and repainting the UI never truly overlap. So it became the view, a background handler, and a data controller, with hardware control in its own module underneath.

  • 요청 큐 · 응답 큐 · 인터럽트 플래그 세 개로만 프로세스 사이를 잇습니다. 화면은 요청을 큐에 넣고 바로 돌아오고, 결과는 워커 스레드가 응답 큐에서 받아 화면에 반영합니다. 공유 메모리를 직접 만지지 않으니 경쟁 상태를 따로 막을 일이 없었습니다.The processes are joined by exactly three things: a request queue, a response queue and an interrupt flag. The UI enqueues a request and returns immediately; a worker thread picks the result off the response queue and paints it. Nothing touches shared memory directly, so there was no race to defend against.
  • 인터럽트 플래그가 핵심이었습니다. 체온은 4회 측정해 평균을 내는데 그 사이 사람이 떠날 수 있습니다. 측정 루프가 매 회차마다 공유 플래그를 확인해 즉시 중단하고 돌아옵니다. 이게 없으면 떠난 사람의 허공 온도가 정상 체온으로 기록됩니다.The interrupt flag carried the design. A temperature is the average of four readings, and a person can walk away mid-way. The loop checks the shared flag between readings and bails out immediately — without it, the empty air after someone leaves gets recorded as a normal body temperature.
  • 측정 시점은 거리가 정합니다. 적외선 온도계는 거리에 민감해서 아무 때나 읽으면 값이 튑니다. 초음파 센서로 8cm 안쪽에 들어올 때까지 기다린 뒤에야 읽기 시작합니다.Distance decides when to measure. An infrared thermometer is distance-sensitive, so reading at the wrong moment gives nonsense. An ultrasonic sensor holds the loop until the person is within 8 cm.
  • 음성 안내는 TTS로 만들되 문장별로 파일 캐싱했습니다. 라즈베리파이에서는 매번 합성하는 그 한 번이 눈에 띄는 지연입니다.Spoken prompts are synthesised once and cached per sentence — on a Raspberry Pi, generating one each time is a visible pause.

회로도 직접 구성했습니다The circuit is mine too

센서 세 종류를 라즈베리파이 한 대에 물렸습니다. 적외선 온도계는 I2C, NFC 리더는 SPI, 초음파 센서는 GPIO로 각각 다른 방식이라 핀이 겹치지 않게 배치해야 했습니다. 초음파 센서의 Echo 핀은 5V로 돌아오는데 라즈베리파이 GPIO는 3.3V까지만 견디므로, 1kΩ·2kΩ 분압 저항을 넣어 전압을 낮춰 받았습니다.Three kinds of sensor on one Raspberry Pi: the infrared thermometer on I2C, the NFC reader on SPI, the ultrasonic sensor on plain GPIO — three different buses whose pins had to be laid out without collisions. The ultrasonic Echo pin returns 5 V while the Pi’s GPIO tolerates only 3.3 V, so a 1 kΩ / 2 kΩ divider drops it before it reaches the board.

서버는 Express REST API로 단말 요청을 받고, 구성원별·일자별 체온을 ejs로 시각화했습니다.The server takes the kiosk’s requests over an Express REST API and renders temperatures per person and per day with ejs.
