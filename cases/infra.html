51개 애플리케이션의 k3s 전환Moving 51 applications to k3s

EC2에 흩어져 있던 애플리케이션 51개를 직접 구축한 k3s 클러스터로 옮기고, 배포 경로를 GitOps로 표준화했습니다. 비용과 조직 규모를 근거로 EKS 대신 k3s를 택했습니다.Fifty-one applications scattered across EC2 moved onto a k3s cluster I built, with every deploy path standardised on GitOps. The choice of k3s over EKS was made on cost and team size.

배경Background

플로버에는 서비스가 하나였습니다. 공간히어로를 EC2에 올리고 스크립트로 배포하면 충분했습니다.Flover had one service. Putting Gonggan Hero on EC2 and deploying with scripts was enough.

제로콜이 붙고 그 아래로 메시징·결제 서비스가 늘면서 상황이 달라졌습니다. 인프라를 전담하는 사람은 따로 없었습니다.Then ZeroCall arrived, with messaging and billing services under it. There was no one whose job was infrastructure.

문제 — 서비스 증가와 흩어진 배포The problem — more services, scattered deploys

공간히어로만 있을 때는 EC2에 앱을 올리고 스크립트로 배포하면 충분했습니다. 그런데 제로콜이 붙고, 그 아래로 메시징·결제 서비스가 늘어나면서 상황이 달라졌습니다.With only Gonggan Hero, putting apps on EC2 and deploying with scripts was enough. Then ZeroCall arrived, and messaging and billing services under it.

무엇이 어디에 떠 있는지 한 번에 볼 수 없고, 서비스마다 배포 방식이 다르고, 매니페스트가 공간히어로 저장소 안에 제로콜 것까지 들어 있는 이상한 구조가 되었습니다.Nobody could see at a glance what was running where, each service deployed slightly differently, and ZeroCall’s manifests were living inside the Gonggan Hero repository.

EKS가 아니라 k3sk3s, not EKS

관리형 쿠버네티스는 편하지만 컨트롤 플레인 요금이 고정으로 붙습니다. 우리는 노드 몇 대로 시작하는 규모였고, 인프라를 전담하는 사람이 따로 있지도 않았습니다. 그 조건에서 컨트롤 플레인 값을 매달 내는 것은 비용 대비 얻는 것이 적다고 판단했습니다.Managed Kubernetes is comfortable, but the control plane is a fixed monthly bill. We were starting at a handful of nodes, with no dedicated infrastructure person. Paying for a control plane at that size buys less than it costs.

k3s는 컨트롤 플레인이 노드 위에 얹히므로 그 비용이 없습니다. 대신 컨트롤 플레인의 건강을 우리가 책임져야 하고, etcd 멤버 수 같은 것을 직접 알아야 합니다. 트레이드오프를 알고 고른 것이고, 그 근거를 저장소에 적어 두었습니다 — 나중에 누가 보든 "왜 EKS가 아닌가"에 답이 있어야 하기 때문입니다.In k3s the control plane rides on the nodes, so that cost disappears — in exchange for owning its health and knowing things like how many etcd members you should have. It was a trade-off chosen deliberately, and written down in the repository, so that whoever reads it later finds an answer to "why not EKS".

클러스터 구성The cluster

용량이 필요하면 server가 아니라 agent를 늘립니다. server 수는 곧 etcd 멤버 수이고, etcd는 Raft라 3 다음은 5입니다 — 4는 3과 똑같이 한 대만 버티면서 쓰기만 느려집니다. 이런 것들은 한 번 잘못 늘리면 되돌리기가 번거로워서 저장소에 명시해 두었습니다.When capacity is needed we add agents, not servers. The server count is the etcd member count, and etcd is Raft: after three comes five — four tolerates exactly as many failures as three while making writes slower. Mistakes like that are awkward to undo, so the rule is written into the repository.

노드 한 대가 흔들리면 사용자 25%가 실패하던 구조The setup where one shaky node failed a quarter of users

처음에는 도메인 A레코드에 노드 EIP 네 개를 나열한 라운드로빈 DNS였습니다. 싸고 간단했지만 DNS에는 헬스체크가 없습니다. 2026년 8월 말, 노드 한 대가 흔들리자 그 IP를 고른 사용자 25%가 그대로 실패했습니다.It began as round-robin DNS: four node EIPs listed on the domain’s A record. Cheap and simple, but DNS has no health check. At the end of August 2026 one node wobbled, and the quarter of users whose resolver picked that IP simply failed.

앞단에 NLB를 세웠습니다. L4 패스스루라 TLS를 건드리지 않으므로, cert-manager가 발급한 인증서를 Traefik이 그대로 제시합니다. 인증서 관리 위치를 바꾸지 않고 헬스체크만 얻었습니다.An NLB now sits in front. Because it passes through at L4 it never touches TLS, so Traefik still presents the certificate cert-manager issued. We gained health checking without moving certificate ownership anywhere.

배포 정책 — 의도된 수동 동기화Release policy — manual sync by design

CI는 이미지를 굽고 태그만 커밋합니다. Argo CD는 그 차이를 "동기화되지 않음"으로 표시한 채 기다립니다. 사람이 누르면 반영됩니다. 이미지는 항상 최신이고, 배포 시점은 사람이 정한다는 뜻입니다.CI builds the image and commits only the tag. Argo CD marks the drift as out of sync and waits. A person presses sync. The image is always current; when it ships is a human decision.

예외는 랜딩 페이지 세 개입니다. 정적 마케팅 페이지라 롤백이 싸고 배포가 잦아서 자동으로 두었습니다. 다만 Argo의 기본 폴링 주기가 3분이라 "즉시"가 아니라 최대 3분 지연이라는 점도 적어 두었습니다 — 이런 사항을 기록해 두지 않으면 나중에 누군가 "배포가 안 된다"고 30분을 씁니다.The exception is three landing pages: static marketing sites where rollback is cheap and releases are frequent, so they sync automatically. The note also says that Argo polls every three minutes, so "automatic" means up to three minutes late — without that line, someone eventually spends half an hour deciding the deploy is broken.

  • GitHub Actions는 클러스터 API에 접근하지 않습니다. 클러스터가 git을 당겨옵니다. 그래서 6443 포트를 외부에 열 필요가 없고, 나중에 온프레미스로 옮겨도 그대로 동작합니다.GitHub Actions never reaches the cluster API. The cluster pulls from git instead, so port 6443 is never exposed — and the same setup keeps working if this moves on-premise.
  • 이미지 태그는 커밋 SHA로 고정합니다. latest 같은 가변 태그를 쓰면 Argo가 변경을 감지하지 못하고, 지금 무엇이 떠 있는지도 알 수 없습니다.Tags are pinned to commit SHAs. A moving tag like latest hides changes from Argo and makes it impossible to say what is actually running.
  • Argo Application은 인프라 저장소에, 매니페스트는 각 서비스 저장소에 둡니다. Application은 포인터일 뿐이고, 태그를 커밋하는 주체가 각 서비스 CI이기 때문입니다. 한곳에 모으면 모든 CI가 인프라 저장소 권한을 들고 서로 부딪칩니다.Argo Applications live in the infrastructure repository; manifests live with their service. An Application is just a pointer, and it is each service’s CI that commits the tag. Centralising manifests would hand every CI write access here and make them collide.
  • 비밀값은 SealedSecret으로 저장소에 들어갑니다. 클러스터 안에서만 풀 수 있으므로 git에 올려 두고 관리할 수 있습니다.Secrets are committed as SealedSecrets — only the cluster can open them, so they can live in git like everything else.

운영 원칙 — 알려진 제약의 문서화Operating principle — documenting known limitations

이 클러스터에는 아직 고치지 못한 것들이 있습니다. 저장소에 TODO.md를 두고 무엇이 문제이고 왜 지금 그 상태인지를 근거와 함께 적어 둡니다. 숨기면 다음 사람이 같은 함정을 다시 밟습니다.This cluster still has unfixed problems. A TODO.md in the repository records what is wrong and why it is currently that way, with the reasoning. Hidden, they become traps the next person walks into.
