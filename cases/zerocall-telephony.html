배경Background

제로콜은 070 번호로 전화와 문자를 주고받고, AI가 대신 응대하는 서비스입니다. 2025년 11월에 시작했으며, Asterisk를 올리고 다이얼플랜을 쓰고 call-handler를 ARI로 붙이는 초기 구성부터 맡았습니다.ZeroCall is a 070 phone and messaging service with an AI that answers. It began in November 2025. I owned it from the initial build — standing up Asterisk, writing the dialplan, attaching the call-handler over ARI.

오랫동안 Asterisk 한 대가 모든 통화를 받았습니다. 사용자가 수백 명일 때는 충분한 구조였지만, 지점이 여럿인 학원을 받기에는 이중화가 필요했습니다.For a long time one Asterisk answered every call. That was sound at a few hundred users, but taking on a multi-branch academy called for redundancy.

무엇이 문제였나The problem

오랫동안 Asterisk 한 대가 전화를 전부 받았습니다. 사용자가 수백 명일 때는 충분했지만, 메가스터디 지점이 붙으면서 그 한 대가 급소가 되었습니다. 재시작 한 번이 여러 학원의 전화를 동시에 끊을 수 있는 구조였습니다.For a long time one Asterisk answered every call. Fine at a few hundred users — but once Megastudy branches connected, that box became the weak point. A single restart could have taken several academies down together.

증설이 필요한 이유는 처리량이 아니라 가용성이었습니다. 대기자는 서버에 거의 부담을 주지 않고, 먼저 막히는 것은 통신사와 계약한 인입 채널 수입니다. 늘려야 할 것은 처리 용량이 아니라 급소의 개수였습니다.The reason to add machines was availability, not throughput. Waiting callers cost almost nothing, and the real ceiling is the carrier’s inbound channel count. What needed multiplying was not capacity but the number of single points of failure.

주소를 바꾸지 않고 옮기기Moving without changing an address

통신사에는 우리 주소 하나가 등록되어 있고, 앱과 데스크폰은 고정된 도메인 하나로 붙습니다. 그게 바뀌면 통신사와 다시 협의하고 현장 전화기를 한 대씩 만져야 합니다.The carrier has one of our addresses on file, and apps and desk phones connect to a single fixed domain. Change either and you renegotiate with the carrier and visit every handset.

그래서 원칙은 하나였습니다 — Kamailio가 Asterisk의 포트를 그대로 이어받고, Asterisk가 뒤로 비켜난다.So the rule was singular: Kamailio inherits Asterisk’s ports, and Asterisk steps aside.

  • Asterisk의 외부 트랜스포트는 삭제하지 않고 이동만 했습니다. 삭제하면 이를 참조하던 엔드포인트가 깨지고 롤백도 할 수 없습니다.Asterisk’s transports were moved, never deleted — deleting breaks every endpoint referencing them and leaves no way back.
  • 이 단계는 리로드가 아니라 재시작이어야 합니다. PJSIP은 리로드로 트랜스포트를 다시 바인딩하지 못해, 사라진 소켓이 남아 새 Kamailio가 포트를 못 잡습니다.This step must be a restart, not a reload — PJSIP cannot rebind transports, so the old socket lingers and Kamailio cannot claim the port.

구조와 통화 소유권Architecture and call ownership

누가 그 통화의 주인인가Who owns the call

분배기는 대기열을 공유 저장소에 두고 돕니다. 노드가 여럿이 되면 문제가 생깁니다 — A노드가 B노드에 붙은 대기자를 꺼내면, 그 채널을 만질 수 없어 통화를 잃습니다.The distributor works off a shared queue. With several nodes: if node A pops a caller attached to node B, it cannot touch that channel and the call is lost.

처음에는 그룹 어피니티로 막았습니다. 착신번호를 해시해 한 지점의 통화를 한 노드에 고정하면, 남의 대기자를 꺼낼 일이 없어집니다.My first answer was group affinity — hash the dialled number, pin a branch to one node, never pop someone else’s caller.

하루 만에 제거했습니다. 꺼내는 일 자체를 소유자 기준으로 바꾸면 되는 문제였기 때문입니다. 큐 항목마다 그 통화를 쥔 인스턴스를 적어 두고, 각 노드는 자기가 주인인 대기자만 꺼냅니다.I removed it a day later. The real fix was to make the dequeue ownership-aware: each entry records the instance holding the call, and a node pops only what it owns.

어피니티의 이유는 하나뿐이었고, 그 이유는 사라졌습니다. 반면 비용은 실재했습니다 — 고정에 쓰던 테이블 때문에 Kamailio 기동이 DB 뷰에 의존하게 됩니다. 운영 DB엔 그 뷰가 없어 그대로면 배포도 막혔습니다. 사용하지 않는 기능을 위해 그 위험을 감수하는 것은 합리적이지 않습니다.Affinity had exactly one reason, and it was gone. The cost was real: the pinning table made Kamailio’s startup depend on a database view that production did not have — it would have blocked the release. Carrying that risk for a feature nobody uses is not a reasonable trade.

The queue inflates, hits its cap, and starts rejecting good callers. Each node writes a periodic liveness marker; entries from a node that stopped are swept by the others.

두 대가 한 대기열을 나눠 쓸 때When two nodes share one queue

소유권은 "남의 통화를 만지지 않는다"까지만 보장합니다. 분배기가 둘이 되면 반대쪽에서 문제가 하나 더 생깁니다 — 두 분배기가 같은 상담원을 동시에 고르면, 한 사람의 전화가 두 번 울립니다.Ownership only guarantees that nobody touches someone else’s call. With two distributors, a second problem appears from the other side: if both pick the same agent at the same moment, one person’s phone rings twice.

막는 장치는 원래 다 있었습니다 — 프로세스 메모리에요. 한 대일 때는 그걸로 충분했지만, 두 대가 되면 락도 예약도 상대 노드에게는 보이지 않습니다. Redis로 옮기는 것 자체는 일이 아니었습니다. 옮기면서 의미가 바뀌지 않게 하는 것이 일이었습니다.The guards already existed — in process memory. Fine with one node; with two, neither the lock nor the reservation is visible to the other side. Moving them into Redis was not the work. Keeping their meaning intact through the move was.

분 단위로 도는 루프에 거는 락Locking a loop that runs for minutes

분배 루프는 링 타임아웃을 기다리며 분 단위로 돕니다. TTL 하나로는 안 됩니다 — 짧으면 일하는 도중에 풀리고, 길면 죽은 주인을 그만큼 기다립니다. 그래서 루프를 돌 때마다 연장하고, 연장에 실패하면 — 락을 잃었다는 뜻이므로 — 그 자리에서 멈춥니다. 해제는 compare-and-delete입니다. 그냥 지우면, TTL이 지나 다른 노드가 새로 잡은 락을 뒤늦게 끝난 쪽이 지워 버립니다.The distribution loop runs for minutes at a time, waiting out ring timeouts. One TTL cannot cover that — too short and the lock expires mid-work, too long and everyone waits on a dead owner. So the lock is renewed on every pass, and a failed renewal — which means the lock is lost — stops the loop where it stands. Release is compare-and-delete: a plain delete lets the slow finisher erase a lock some other node has since acquired.

그룹으로는 못 막는 것What no group boundary can fence

락의 축은 그룹인데, 상담원은 사람입니다. 운영에는 여러 그룹을 겸하는 상담원이 51명 있고(많게는 48개 그룹), 이들은 서로 다른 노드에서 동시에 후보가 됩니다. 통화중 표시는 링이 걸린 뒤에야 찍히므로 "골랐지만 아직 안 울린" 1~2초의 창이 남습니다. 그 창을 덮는 것이 배정 예약입니다.The lock’s axis is the group; an agent is a person. Fifty-one agents in production belong to several groups at once (up to 48), so they come up as candidates on different nodes simultaneously. The busy flag is only written once the ring is placed, which leaves a one-to-two-second window between choosing an agent and ringing them. Covering that window is the reservation’s whole job.

이 예약을 Redis로 옮기며 한 번 틀렸습니다. 조건 없는 SET을 썼는데, 그것은 선점이 아니라 표시일 뿐입니다. 인메모리 Set 시절에는 add가 동기라 틈이 없었지만, 네트워크를 건너는 순간 판정과 기록 사이가 벌어집니다. SET NX로 바꿔 이긴 쪽만 진행하고, 진 쪽은 다음 후보로 넘어갑니다.Moving it to Redis, I got this wrong once. I used an unconditional SET — which is a note, not a claim. When this was an in-memory Set, add was synchronous and there was no gap; the moment a network sits in between, the check and the write come apart. It is now SET NX: the winner proceeds, the loser moves on to the next candidate.

테스트 목(mock)도 NX 의미를 지키게 고쳤습니다. 목이 항상 성공을 돌려주면 "두 노드가 같은 사람을 고르지 않는다"는 실패할 수 없는 검증이 되어 버립니다.The test mocks were fixed to honour NX semantics too. A mock that always succeeds turns “two nodes never pick the same person” into a test that cannot fail.

주인 없는 통화들The calls that had no owner

정작 소유권을 적는 곳은 분배기 하나뿐이었습니다. 큐를 쓰지 않는 그룹이 365개 중 349개, AI 응대, 착신전환 — 대부분의 통화가 주인 없이 다니고 있었고, 노드가 둘이면 그 통화의 전환·당겨받기는 절반 확률로 실패합니다. 경로 세 곳에 기록을 심는 대신, 그 Asterisk의 모든 채널을 이미 보고 있는 한 곳에서 적게 했습니다. 빠뜨릴 자리가 없는 위치가 정답이었습니다.Yet ownership was being written in exactly one place — the distributor. 349 of 365 groups never touch the queue; AI calls and forwarded calls skip it too. Most calls were travelling with no owner, and with two nodes their transfer and pickup fail half the time. Rather than planting a write into each of three paths, the record now happens in the one service that already watches every channel on that Asterisk — the place with nowhere left to forget.

재시작 복구도 같은 기준으로 좁혔습니다. 전역 복구는 한 대일 때는 "아무도 못 돌보는 통화"와 같은 말이지만, 두 대가 되면 한쪽의 재배포가 다른 쪽의 멀쩡한 통화를 실패로 마감하고 대기자를 지웁니다. 이제 각 노드는 자기가 쥐고 있던 것만 정리합니다.Restart recovery narrowed along the same line. With one node, global recovery means “the calls nobody can look after”; with two, redeploying one node closes the other node’s healthy calls as failed and wipes its waiting callers. Each node now cleans up only what it held.

검증은 dev에 두 노드를 세우고 했습니다. 267통을 부어 최대 동시 37통, 상담원 두 명이 정확히 68통씩 — 중복 배정 0, 유실 0.Verified on dev with both nodes up: 267 calls poured in, 37 concurrent at peak, the two test agents taking exactly 68 apiece — zero double assignments, zero calls lost.

통화를 끊지 않고 배포하기Deploying without dropping a call

노드가 하나일 때 배포는 컨테이너 교체, 즉 작은 사고였습니다. 그 노드가 쥔 통화는 끊기고, 교체 창에 들어온 전화는 대기열 없는 폴백으로 떨어집니다 — 전원이 통화 중이면 원래 기다렸을 손님이 그냥 실패합니다. 큐가 가장 필요한 바쁜 시간일수록 더 그랬습니다. 노드가 둘이 되고서야 제대로 할 수 있게 됐습니다. 노드마다 순차로:With one node, a deploy was a container swap — which is to say, a small incident. Calls held by that node died, and calls arriving in the window fell through to a fallback with no queue: with every agent busy, a caller who would have waited simply failed. The busier the hour, the worse it got. Only with a second node could it be done properly. One node at a time:

  • 받아 줄 노드가 있는지 먼저 봅니다. 다른 노드가 이미 죽었는데 나까지 빠지면 전화가 갈 곳이 없습니다 — 그때는 배포를 중단하는 것이 맞습니다.Check that another node can take the traffic. If the other one is already down, pulling this one leaves calls nowhere to go — the right move is to abort the deploy.
  • Kamailio 분배에서 뺍니다. 새 전화는 다른 노드가 대기열까지 그대로 받습니다.Pull the node from Kamailio’s dispatcher. New calls land on the other node with the queue fully intact.
  • 깨질 통화가 빠지기를 기다립니다.Wait for the calls that would actually break.
  • 교체하고, ARI가 붙은 것을 확인한 뒤에 분배로 되돌립니다.Replace the container, confirm ARI is attached, then put the node back.

기다릴 것은 "통화 0"이 아니다The wait is not for zero calls

무엇이 실제로 깨지는지부터 갈랐습니다. 상담원과 연결된 통화는 오디오가 Asterisk 브릿지 안에 있어 교체를 모르고 지나갑니다. 대기 중인 손님은 다음 인스턴스가 이어받습니다. 그 자리에서 깨지는 것은 미디어가 call-handler를 지나는 ARS·AI 통화뿐이고, 기다릴 것도 그것뿐입니다. "전체 통화 0"을 기다리면 바쁜 시간대에는 그 순간이 영영 오지 않습니다.The first question was what actually breaks. A call bridged to an agent rides through the swap — its audio lives inside Asterisk. A waiting caller is adopted by the next instance. What breaks in place is only the IVR and AI calls, whose media runs through call-handler itself — so that is all the wait covers. Wait for “zero calls overall” and, in busy hours, that moment never comes.

교체를 건너는 통화Calls that ride through the swap

그래도 컨테이너가 내려갔다 오는 순간은 있습니다. 재기동한 분배기가 이전 프로세스의 통화를 이어받는데, 순서가 전부입니다.There is still the moment when the container is down. The restarted distributor adopts what the previous process held — and the order is everything.

  • 통화 중인 짝부터. 브릿지가 발신자–상담원 짝을 알려주므로 가장 확정적입니다. 이어받지 않으면 오디오는 멀쩡한데 장부에는 실패로 남고, 그 상담원의 호전환이 조용히 죽습니다.Bridged calls first. The bridge names the caller–agent pair, which makes this the most certain step. Unadopted, the audio stays fine but the books close it as failed — and that agent’s transfer button dies silently.
  • 그다음 남은 링 채널을 고아로 정리. 안 끊으면 그 상담원이 통화중으로 묶여 서비스에서 통째로 빠집니다.Then the orphaned ring channels. Left alone, they mark an agent as busy and take them out of service entirely.
  • 마지막으로 줄 서 있던 손님을 들어온 순서대로.Last, the waiting callers, in the order they arrived.

앞의 둘을 뒤집으면 안 됩니다 — 통화 중인 상담원의 채널도 이름이 같아서, 조건 없이 정리하면 대화 중인 손님이 끊깁니다. 실제로 직전 커밋에 그 순서 버그가 있었고, 다음 커밋에서 잡았습니다.The first two must not be swapped: an agent mid-conversation has a channel with the same name, and an unconditional cleanup hangs up on a live caller. The commit before this one had exactly that bug; the next one caught it.

노드를 빼는 방법에도 함정이 있었습니다. inactive로 빼면 헬스체크 프로빙이 "노드가 멀쩡하네" 하고 2초 만에 되돌립니다. 관리자 결정을 뜻하는 disabled여야 프로빙이 못 뒤집습니다. 배포 러너에게는 노드마다 forced command로 묶은 전용 SSH 키를 줬습니다 — 그 키로 할 수 있는 일은 빼기·되돌리기·상태 조회 셋뿐이고, 넘어온 명령은 셸에 닿기 전에 형태 검사를 통과해야 합니다.Even pulling the node had a trap. Marked inactive, the health-check probing decides the node looks fine and puts it back within two seconds — it has to be disabled, an administrative state probing cannot override. And the deploy runner gets a deliberately narrow key: a per-node SSH key bound to a forced command that can do exactly three things — pull, restore, status — with every incoming command shape-checked before it reaches a shell.

dev에서 대기·중단·회피 경로를 시뮬레이션으로 확인한 뒤, 운영에서 두 노드를 순차 배포해 검증했습니다. 다만 처음 만든 대기 로직은 에러 한 줄 없이 세 가지 방식으로 고장 나 있었습니다 — 그 감사는 에러를 내지 않는 실패에 따로 적었습니다.The waiting, aborting and avoiding paths were exercised in a dev simulation first, then the procedure was verified in production, one node after the other. The wait logic I first wrote, though, turned out to be broken in three ways without raising a single error — that audit is written up in The failures that never raise an error.

현장 교환기 위에 서기Standing on an existing PBX

메가스터디 지점에는 이미 교환기와 전화기가 깔려 있었습니다. 요구는 명확했습니다 — 전화기를 한 대도 바꾸지 않는다.Megastudy’s branches already had an exchange and handsets in place. The requirement was blunt: replace no phones.

처음 세운 전제는 검토 과정에서 무너졌습니다. 그래서 교환기를 건드리지 않고 그 위에 서는 구조로 다시 썼습니다. 제로콜이 ARS·AI·큐·녹음·통계를 맡고, 기존 설비는 내선까지 배달만 합니다.My first assumption did not survive review, so I rewrote the design to sit on top of the exchange without touching it. ZeroCall owns the IVR, the AI, the queue, recording and statistics; the existing equipment only delivers to the extension.

연결은 AWS Site-to-Site VPN으로 사설망을 잇고, SBC 역할은 이미 운영 중인 Kamailio와 rtpengine이 맡습니다. 공인망에 노출하지 않고, 장비도 새로 사지 않았습니다.The link is an AWS site-to-site VPN joining the private networks, with the SBC role played by the Kamailio and rtpengine we already run — nothing exposed publicly, no new hardware bought.

고객사에 요청한 것은 주소 대역 한 줄입니다. SIP를 받는 쪽과 RTP를 받는 쪽, 이중화까지 전부 그 안에 들어가도록 배치했습니다. 방화벽 변경을 다시 요청할 일이 없게 하려는 것이었습니다.What I asked the customer for was a single address range, laid out so that the SIP side, the RTP side and the standby pair all fit inside it. The point was to never have to come back for another firewall change.

지금Where it stands

  • Kamailio 2대 액티브·스탠바이. 장애 시 공인 IP가 유지되어 통신사와 클라이언트 설정은 그대로입니다.Two Kamailio nodes, active/standby. The public IP survives failover, so nothing is reconfigured.
  • Asterisk 3대 부하 분산. 15초 주기로 상태를 확인해 장애 노드를 자동으로 뺍니다.Three Asterisk nodes, health-checked every 15 seconds and dropped automatically on failure.
  • 노드를 늘리는 일이 목록에 한 줄 더하고 리로드가 됐습니다.Adding a node became one line in a list and a reload.
  • 배포는 노드를 하나씩 분배에서 빼서 진행합니다 — 통화를 끊지 않습니다.Deploys go one node at a time, drained from the dispatcher — no call is dropped.
  • 전환 당일 통신사 협의도, 현장 전화기 재설정도 없었습니다.On cutover day there was no call to the carrier and no visit to a handset.
