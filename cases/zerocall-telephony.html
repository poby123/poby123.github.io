전화 인프라 무중단 이중화Zero-downtime redundancy for the telephony stack

단일 Asterisk가 서비스 전체의 단일 장애점이었습니다. Kamailio + rtpengine 앞단을 세워 다중 노드 구조로 전환하면서, 통신사에 등록된 IP와 포트, 현장 전화기 설정은 그대로 유지했습니다.A single Asterisk was a single point of failure for the whole service. I moved it behind a Kamailio + rtpengine front end onto multiple nodes, keeping the IP and ports the carrier has on file — and every on-site handset — exactly as they were.

배경Background

제로콜은 070 번호로 전화와 문자를 주고받고, AI가 대신 응대하는 서비스입니다. 2025년 11월에 시작했으며, Asterisk를 올리고 다이얼플랜을 쓰고 call-handler를 ARI로 붙이는 초기 구성부터 맡았습니다.ZeroCall is a 070 phone and messaging service with an AI that answers. It began in November 2025. I owned it from the initial build — standing up Asterisk, writing the dialplan, attaching the call-handler over ARI.

오랫동안 Asterisk 한 대가 모든 통화를 받았습니다. 사용자가 수백 명일 때는 충분한 구조였지만, 지점이 여럿인 학원을 받기에는 이중화가 필요했습니다.For a long time one Asterisk answered every call. That was sound at a few hundred users, but taking on a multi-branch academy called for redundancy.

무엇이 문제였나The problem

초기에는 Asterisk 한 대가 모든 통화를 처리했습니다. 사용자 수백 명 규모에서는 충분했지만, 메가스터디 지점이 연결되면서 재시작 한 번이 여러 학원의 전화를 동시에 끊을 수 있는 단일 장애점이 되었습니다.Initially a single Asterisk handled every call — sound at a few hundred users. Once Megastudy branches connected, it became a single point of failure where one restart could take several academies down at once.

증설의 목적은 처리량이 아니라 가용성이었습니다. 대기 통화는 서버에 거의 부하를 주지 않고, 실질 상한은 통신사와 계약한 인입 채널 수입니다. 늘려야 할 것은 처리 용량이 아니라 장애점의 수였습니다.The goal was availability, not throughput. Waiting callers cost the server almost nothing, and the real ceiling is the carrier’s contracted inbound channel count. What needed multiplying was the number of failure points, not capacity.

외부 IP·포트를 유지한 전환Cutting over without changing an IP or port

통신사에는 서버의 공인 IP 하나가 등록되어 있고, 앱과 데스크폰은 고정 도메인 하나로 접속합니다. 어느 쪽이든 바뀌면 통신사와 재협의하고 현장 전화기를 한 대씩 재설정해야 합니다.The carrier has one public IP of ours on file, and apps and desk phones connect through a single fixed domain. Changing either means renegotiating with the carrier and reconfiguring handsets one by one.

그래서 전환 원칙을 하나로 정했습니다. Kamailio가 Asterisk의 기존 포트를 그대로 이어받고, Asterisk는 내부 전용 포트로 물러납니다.So the cutover followed one rule: Kamailio inherits Asterisk’s existing ports, and Asterisk retreats to internal-only ones.

  • Asterisk의 외부 트랜스포트는 삭제하지 않고 이동만 했습니다. 삭제하면 이를 참조하던 엔드포인트가 깨지고 롤백도 할 수 없습니다.Asterisk’s transports were moved, never deleted — deleting breaks every endpoint referencing them and leaves no way back.
  • 이 단계는 리로드가 아니라 재시작이어야 합니다. PJSIP은 리로드로 트랜스포트를 다시 바인딩하지 못해, 사라진 소켓이 남아 새 Kamailio가 포트를 못 잡습니다.This step must be a restart, not a reload — PJSIP cannot rebind transports, so the old socket lingers and Kamailio cannot claim the port.

구조와 통화 소유권Architecture and call ownership

통화 소유권 모델The call-ownership model

분배기는 대기열을 공유 저장소에 둡니다. 노드가 여럿이면 A노드가 B노드에 붙은 대기자를 꺼내는 순간 그 채널을 제어할 수 없어 통화를 잃습니다.The distributor works off a shared queue. With several nodes, the moment node A pops a caller attached to node B, it cannot control that channel and the call is lost.

처음에는 그룹 어피니티로 막았습니다. 착신번호를 해시해 한 지점의 통화를 한 노드에 고정하면, 남의 대기자를 꺼낼 일이 없어집니다.My first answer was group affinity — hash the dialled number, pin a branch to one node, never pop someone else’s caller.

하루 만에 제거했습니다. 꺼내는 일 자체를 소유자 기준으로 바꾸면 되는 문제였기 때문입니다. 큐 항목마다 그 통화를 쥔 인스턴스를 적어 두고, 각 노드는 자기가 주인인 대기자만 꺼냅니다.I removed it a day later. The real fix was to make the dequeue ownership-aware: each entry records the instance holding the call, and a node pops only what it owns.

어피니티의 이유는 하나뿐이었고, 그 이유는 사라졌습니다. 반면 비용은 실재했습니다 — 고정에 쓰던 테이블 때문에 Kamailio 기동이 DB 뷰에 의존하게 됩니다. 운영 DB엔 그 뷰가 없어 그대로면 배포도 막혔습니다. 사용하지 않는 기능을 위해 그 위험을 감수하는 것은 합리적이지 않습니다.Affinity had exactly one reason, and it was gone. The cost was real: the pinning table made Kamailio’s startup depend on a database view that production did not have — it would have blocked the release. Carrying that risk for a feature nobody uses is not a reasonable trade.

다중 노드 동시성 — 링은 정확히 한 번Multi-node concurrency — exactly one ring

소유권 모델은 다른 노드의 통화를 건드리지 않는 것까지만 보장합니다. 분배기가 둘이 되면 반대 방향의 문제가 남습니다. 두 분배기가 같은 상담원을 동시에 선택하면 한 사람의 전화가 두 번 울립니다.The ownership model only guarantees that no node touches another node’s call. With two distributors a problem remains in the other direction: if both select the same agent at the same moment, that person’s phone rings twice.

이를 막는 락과 예약은 이미 있었지만, 프로세스 메모리에 있어 상대 노드에서는 보이지 않았습니다. Redis로 옮기는 작업의 핵심은 코드 이전이 아니라 옮긴 뒤에도 원자성의 의미가 그대로 유지되게 하는 것이었습니다.The lock and the reservation that prevent this already existed — in process memory, invisible to the other node. The substance of moving them into Redis was not the porting itself but preserving their atomicity semantics through the move.

분 단위로 도는 루프에 거는 락Locking a loop that runs for minutes

분배 루프는 링 타임아웃을 기다리며 분 단위로 실행되므로 고정 TTL로는 부족합니다. 짧으면 작업 도중에 풀리고, 길면 죽은 소유자를 그만큼 기다리게 됩니다. 그래서 루프마다 락을 연장하고, 연장 실패는 락 상실로 간주해 즉시 중단합니다. 해제는 compare-and-delete로 처리했습니다. 단순 삭제로는 TTL 만료 후 다른 노드가 새로 획득한 락을 늦게 끝난 쪽이 지울 수 있기 때문입니다.The distribution loop runs for minutes at a time waiting out ring timeouts, so a fixed TTL is not enough: too short and the lock expires mid-work, too long and everyone waits on a dead owner. So the lock is renewed on every pass, and a failed renewal is treated as loss of the lock and stops the loop immediately. Release is compare-and-delete — a plain delete would let a slow finisher erase a lock another node has since acquired.

사람 축의 경합 — SET NX 선점Contention on the person axis — claiming with SET NX

락의 축은 그룹이지만 상담원은 사람입니다. 운영 환경에는 여러 그룹을 겸하는 상담원이 51명(최대 48개 그룹) 있어, 이들은 서로 다른 노드에서 동시에 후보가 됩니다. 통화중 표시는 링이 걸린 뒤에야 기록되므로, 선택과 링 사이 1~2초의 공백이 남습니다. 이 공백을 덮는 것이 배정 예약입니다.The lock’s axis is the group, but an agent is a person. Fifty-one agents in production belong to several groups at once (up to 48), so they surface as candidates on different nodes simultaneously. The busy flag is only recorded after the ring is placed, leaving a one-to-two-second gap between selection and ring — the gap the reservation exists to cover.

예약을 Redis로 옮기는 과정에서 조건 없는 SET을 썼다가 이 공백을 다시 여는 회귀를 만들었습니다. 조건 없는 SET은 선점이 아니라 표시에 불과합니다. 인메모리 Set에서는 add가 동기적이라 판정과 기록 사이에 틈이 없었지만, 네트워크를 거치는 순간 둘이 분리됩니다. SET NX 선점으로 바꿔 이긴 쪽만 진행하고, 진 쪽은 다음 후보로 넘어가게 했습니다.Porting the reservation to Redis, I introduced a regression by using an unconditional SET — which is a note, not a claim. In the in-memory Set, add was synchronous and there was no gap; the moment a network sits in between, check and write come apart. Switching to a SET NX claim, only the winner proceeds and the loser moves on to the next candidate.

테스트 목(mock)도 NX 의미를 지키도록 함께 고쳤습니다. 항상 성공하는 목 아래에서는 "두 노드가 같은 사람을 고르지 않는다"가 실패할 수 없는 검증이 되기 때문입니다.The test mocks were fixed to honour NX semantics as well — under a mock that always succeeds, “two nodes never pick the same person” becomes a test that cannot fail.

소유권 기록의 공백The gap in ownership records

점검해 보니 소유권을 기록하는 곳이 분배기 하나뿐이었습니다. 큐를 쓰지 않는 그룹 365개 중 349개, AI 응대, 착신전환 통화가 모두 소유자 없이 처리되고 있었고, 이 상태로 노드를 늘리면 해당 통화의 전환·당겨받기가 절반 확률로 실패합니다. 경로 세 곳에 기록을 각각 추가하는 대신, 그 Asterisk의 모든 채널을 이미 구독하고 있는 서비스 한 곳에서 기록하도록 옮겼습니다. 누락될 자리가 없는 위치를 고르는 것이 핵심이었습니다.An audit showed ownership being written in exactly one place — the distributor. 349 of 365 groups never touch the queue, and AI and forwarded calls skip it too, so most calls carried no owner; with two nodes, their transfer and pickup would fail half the time. Rather than adding a write to each of three paths, the record moved to the one service that already subscribes to every channel on that Asterisk — choosing the position with nowhere left to forget.

재시작 복구의 범위도 같은 기준으로 좁혔습니다. 단일 노드에서 전역 복구는 "돌볼 주체가 사라진 통화의 정리"와 같은 뜻이지만, 노드가 둘이면 한쪽의 재배포가 다른 쪽의 정상 통화를 실패로 마감하고 대기자를 지웁니다. 이제 각 노드는 자신이 소유했던 통화만 정리합니다.Restart recovery narrowed along the same line. With one node, global recovery means cleaning up calls nobody is left to look after; with two, redeploying one node closes the other’s healthy calls as failed and wipes its waiting callers. Each node now cleans up only the calls it owned.

검증은 2노드 dev 환경에서 진행했습니다. 267통을 투입해 최대 동시 37통 상황에서 중복 배정 0건, 통화 유실 0건을 확인했고, 상담원 두 명에게 정확히 68통씩 균등 분배되었습니다.Verification ran on a two-node dev environment: 267 calls at up to 37 concurrent, with zero double assignments and zero calls lost, and the two test agents taking exactly 68 calls apiece.

무중단 배포 절차The zero-downtime release procedure

노드가 하나일 때는 배포가 곧 컨테이너 교체였습니다. 그 노드가 처리 중이던 통화는 끊기고, 교체 중 유입된 통화는 대기열 없는 폴백으로 처리되어 상담원이 모두 통화 중이면 그대로 실패했습니다. 통화량이 많은 시간대일수록 피해가 컸습니다. 노드가 둘이 된 뒤 배포 절차를 다음과 같이 재설계했습니다. 노드마다 순차로:With a single node, a deploy meant replacing the container: calls it was handling died, and calls arriving during the swap fell through to a queue-less fallback — with every agent busy, a caller who would have waited simply failed. The busier the hour, the greater the damage. With a second node available, the procedure was redesigned as follows, one node at a time:

  • 받아 줄 노드가 있는지 먼저 봅니다. 다른 노드가 이미 죽었는데 나까지 빠지면 전화가 갈 곳이 없습니다 — 그때는 배포를 중단하는 것이 맞습니다.Check that another node can take the traffic. If the other one is already down, pulling this one leaves calls nowhere to go — the right move is to abort the deploy.
  • Kamailio 분배에서 뺍니다. 새 전화는 다른 노드가 대기열까지 그대로 받습니다.Pull the node from Kamailio’s dispatcher. New calls land on the other node with the queue fully intact.
  • 깨질 통화가 빠지기를 기다립니다.Wait for the calls that would actually break.
  • 교체하고, ARI가 붙은 것을 확인한 뒤에 분배로 되돌립니다.Replace the container, confirm ARI is attached, then put the node back.

대기 기준 — 실제로 깨지는 통화만What the wait covers — only the calls that break

먼저 무엇이 실제로 깨지는지를 구분했습니다. 상담원과 연결된 통화는 오디오가 Asterisk 브릿지 안에 있어 교체의 영향을 받지 않고, 대기 중인 고객은 다음 인스턴스가 이어받습니다. 교체 시점에 깨지는 것은 미디어가 call-handler를 경유하는 ARS·AI 통화뿐이므로, 대기 조건도 그 통화로 한정했습니다. "전체 통화 0"을 기다리는 방식으로는 바쁜 시간대에 그 시점이 오지 않습니다.The first step was separating what actually breaks. A call bridged to an agent is unaffected — its audio lives inside Asterisk — and a waiting caller is adopted by the next instance. What breaks at swap time is only IVR and AI calls, whose media passes through call-handler, so the wait condition covers exactly those. Waiting for “zero calls overall” never terminates in busy hours.

재기동 시 통화 이어받기Adopting calls across a restart

그래도 컨테이너가 내려갔다 올라오는 구간은 존재합니다. 재기동한 분배기가 이전 프로세스의 통화를 이어받는데, 이어받는 순서가 결과를 좌우합니다.There is still a window while the container is down. The restarted distributor adopts what the previous process held — and the order of adoption decides the outcome.

  • 통화 중인 짝부터. 브릿지가 발신자–상담원 짝을 알려주므로 가장 확정적입니다. 이어받지 않으면 오디오는 멀쩡한데 장부에는 실패로 남고, 그 상담원의 호전환이 조용히 죽습니다.Bridged calls first. The bridge names the caller–agent pair, which makes this the most certain step. Unadopted, the audio stays fine but the books close it as failed — and that agent’s transfer button dies silently.
  • 그다음 남은 링 채널을 고아로 정리. 안 끊으면 그 상담원이 통화중으로 묶여 서비스에서 통째로 빠집니다.Then the orphaned ring channels. Left alone, they mark an agent as busy and take them out of service entirely.
  • 마지막으로 줄 서 있던 손님을 들어온 순서대로.Last, the waiting callers, in the order they arrived.

①과 ②의 순서를 뒤집으면 안 됩니다. 통화 중인 상담원의 채널도 링 채널과 이름이 같아, 조건 없는 정리에 걸리면 대화 중인 고객이 끊깁니다. 실제로 이 순서 오류가 한 커밋에 들어갔고, 검증 과정에서 발견해 다음 커밋으로 바로잡았습니다.Steps one and two must not be swapped: an agent’s in-call channel shares its name with ring channels, and an unconditional cleanup hangs up on a live caller. Exactly that ordering bug landed in one commit; verification caught it and the next commit fixed it.

노드 제외 방식에도 함정이 있었습니다. inactive 상태는 헬스체크 프로빙이 정상 노드로 판정해 2초 만에 되돌리므로, 프로빙이 뒤집을 수 없는 관리자 상태인 disabled를 써야 합니다. 배포 러너에는 노드별 forced-command SSH 키를 발급해 제외·복귀·상태 조회 세 명령만 허용했고, 전달된 명령 문자열은 셸에 닿기 전에 형식 검사를 거칩니다.Even removing the node had a trap: marked inactive, health-check probing judges the node healthy and restores it within two seconds, so it must be disabled — an administrative state probing cannot override. The deploy runner holds a per-node forced-command SSH key allowing exactly three commands — remove, restore, status — and every incoming command string is shape-checked before it reaches a shell.

대기·중단·회피 경로를 dev 시뮬레이션으로 확인한 뒤, 운영에서 두 노드를 순차 배포해 절차를 검증했습니다. 처음 작성한 대기 로직이 에러 없이 세 가지 방식으로 잘못 동작하고 있었던 점검 기록은 별도 케이스 스터디에 정리했습니다.The waiting, aborting and avoiding paths were exercised in a dev simulation, then the procedure was verified in production one node at a time. The audit that found the first version of the wait logic failing silently in three ways is written up in a separate case study.

현장 교환기 위에 서기Standing on an existing PBX

메가스터디 지점에는 이미 교환기와 전화기가 깔려 있었습니다. 요구는 명확했습니다 — 전화기를 한 대도 바꾸지 않는다.Megastudy’s branches already had an exchange and handsets in place. The requirement was blunt: replace no phones.

초기 설계의 전제는 검토 과정에서 성립하지 않는 것으로 확인되어, 교환기를 변경하지 않고 그 위에 얹히는 구조로 다시 설계했습니다. 제로콜이 ARS·AI·큐·녹음·통계를 맡고, 기존 설비는 내선까지의 전달만 담당합니다.The initial design’s premise did not survive review, so it was redesigned to sit on top of the exchange without modifying it. ZeroCall owns the IVR, AI, queue, recording and statistics; the existing equipment only delivers to the extension.

연결은 AWS Site-to-Site VPN으로 사설망을 잇고, SBC 역할은 이미 운영 중인 Kamailio와 rtpengine이 맡습니다. 공인망에 노출하지 않고, 장비도 새로 사지 않았습니다.The link is an AWS site-to-site VPN joining the private networks, with the SBC role played by the Kamailio and rtpengine we already run — nothing exposed publicly, no new hardware bought.

고객사에 요청한 것은 주소 대역 한 줄입니다. SIP를 받는 쪽과 RTP를 받는 쪽, 이중화까지 전부 그 안에 들어가도록 배치했습니다. 방화벽 변경을 다시 요청할 일이 없게 하려는 것이었습니다.What I asked the customer for was a single address range, laid out so that the SIP side, the RTP side and the standby pair all fit inside it. The point was to never have to come back for another firewall change.
